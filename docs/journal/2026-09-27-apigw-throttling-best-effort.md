# 2026-09-27: API Gatewayのスロットリングは設定値どおりには効かない(503と429の切り分け)

## つまずいた箇所
HTTP APIのステージに、スロットリング(rate 1 rps、burst 5)を設定した([ADR-0036](../adr/0036-public-url-protection.md))。効いているかを確かめるため、公開URLに20回を同時に送ったところ、期待した`429 Too Many Requests`は1回も返らず、`200`が6回、`503`が14回返った。

## 原因の切り分け
手元の結果だけでは、どの層で止まったのか分からない。CloudWatchのメトリクスを、層ごとに見た。

| 指標 | 値 | 読み取れること |
|---|---|---|
| API Gatewayの`Count` | 16 | リクエストはAPI Gatewayに届いている |
| API Gatewayの`4xx` | 0 | 1層目(スロットリング)は、1回も429を返していない |
| Lambdaの`ConcurrentExecutions`(最大) | 5 | 予約した同時実行数の上限に達した |
| Lambdaの`Throttles` | 13 | 上限を超えた分を、Lambdaが拒否した |
| API Gatewayの`5xx` | 14 | Lambdaに拒否された分を、API Gatewayが503として返した |

同時に20回送ったので、Lambdaがインスタンスを20個起動しようとして、2層目(同時実行数の予約5)で詰まっていた。503は、2層目が働いた結果だった。

条件を分けるため、次に順番に15回送った。429は1回だけだった。さらに、3本の並列で20秒間送り続けた。

| 送った回数 | 200 | 429 |
|---|---|---|
| 862回(1秒あたり約43回) | 120回(1秒あたり約6回) | 742回 |

負荷をかけ続けると、1層目は86%を429で止めていた。ただし、通った数は1秒あたり約6回で、設定値(1 rps)の約6倍だった。

## 原因
API Gatewayのスロットリングは、ベストエフォート。複数のサーバーがそれぞれ回数を数えるので、厳密な上限にはならない。設定値が小さいほど、この誤差が相対的に大きく出る。

## 対応
設定は変えず、料金の見積もりを、設定値ではなく実測値(約6 rps)で計算し直した(最悪の場合で月$4〜6 → 月$25前後)。予算アラート(月$10)が、この最悪の場合に予測の通知で先に気づけることを確認した。詳しくは[ADR-0036](../adr/0036-public-url-protection.md)の「実装時の検証」。

## 学び
- 「設定した」と「効いている」は別物。防御の設定は、実際に負荷をかけて確かめる
- エラーのステータスコード(429か503か)で、どの層で止まったかの見当がつく。429ならAPI Gatewayのスロットリング、503ならLambdaの同時実行数(Lambdaに拒否された分をAPI Gatewayが503として返す)
- 手元の結果だけで判断せず、メトリクスで層ごとに数字を見ると、原因を切り分けられる。ネットワークの障害で、区間ごとに疎通を確かめていくのと同じ考え方
- 同時に大量に送るテストは、スロットリングだけでなく、コールドスタートや同時実行数の上限も一緒に巻き込む。確かめたいものに合わせて、送り方(同時、順番、継続)を変える
