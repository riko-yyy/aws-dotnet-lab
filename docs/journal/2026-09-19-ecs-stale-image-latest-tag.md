# 2026-09-19: ECRに新しいイメージをpushしたのに、ECSが古いイメージのまま起動した

## つまずいた箇所
Dockerfile修正(非root化)後、ECRに新しいイメージを `:latest` タグでpushしてから `Desired tasks` を `0→1` にしてタスクを起動したところ、起動したタスクの `imageDigest` が**新しくpushしたイメージではなく、1つ前の古いイメージ**のものだった。

タスクのPull開始時刻(21:09)はpush完了時刻(21:07)より後だったため、素直に考えれば新しいイメージが取得されるはずだった。

## 原因(推測)
断定はできていないが、Fargate側に何らかのイメージキャッシュ機構があり、`:latest` のようなミュータブル(可変)なタグに対して、タグ名だけを見て以前解決済みのdigestを再利用してしまうケースがあると考えられる。ECRのタグ自体は正しく新しいdigestを指していた(`aws ecr describe-images` で確認済み)ため、ECR側の問題ではなさそう。

## 解決
`aws ecs update-service --force-new-deployment` を実行し、ECSに明示的に「今のタスクを新しいイメージで入れ替えろ」と指示することで解決した。新しく起動したタスクの `imageDigest` は正しく最新のものになり、CRUD動作も確認できた。

## 学び
- **ECSは、ECRに新しいイメージをpushしても自動では反映しない**(前提として認識していたが、`:latest`タグで新規タスクを起動する場合でも今回のように反映されないケースがあると分かった)
- コードやDockerfileを変更してデプロイし直す際は、pushするだけでなく **`--force-new-deployment` を明示的に叩く**習慣をつけた方が安全
- そもそも本番運用では `:latest` のようなミュータブルタグではなく、gitのコミットハッシュやバージョン番号などの**イミュータブル(不変)なタグ**を使うのが定石とされる理由が、まさに今回のような「どのタグがどの中身を指しているか曖昧になる」問題を避けるためだと実感できた

## 検討したが今回は見送ったこと
ECRリポジトリには「Tag immutability」という設定があり、有効にすると同じタグへの再pushをECR側で拒否できる(今回の問題を構造的に防げる)。今回は学習用途で厳密なバージョン管理までは不要と判断し、`MUTABLE`(デフォルト)のまま維持することにした。タグ運用の見直しは、第5段階(GitHub Actionsによる自動デプロイ)でCI/CDのタグ戦略を設計するタイミングで改めて検討する。
