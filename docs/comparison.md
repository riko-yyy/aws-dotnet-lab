# ECS版とサーバーレス版の比較

同じTODO API(`src/Todo.Api`)を、2つの基盤に載せて比べた。

| | ECS版 | サーバーレス版 |
|---|---|---|
| 実行基盤 | ECS Fargate(タスクにパブリックIPを付与、ALBなし) | Lambda(コンテナイメージ) |
| 入口 | タスクのIPに直接アクセス(8080番) | API Gateway(HTTP API) |
| DB | RDS for PostgreSQL(EF Core) | DynamoDB(オンデマンド) |
| ネットワーク | VPC、パブリックサブネット、プライベートサブネット、セキュリティグループ | なし(VPCを使わない) |
| IaC | Terraform(`infra/ecs/`) | Terraform(`infra/serverless/`) |
| デプロイ | GitHub Actions(`deploy.yml`) | GitHub Actions(`deploy-lambda.yml`) |

数字は、2026年9月に東京リージョンで計測・確認したもの。料金は概算で、税を含まない。

## 1. コードの違い

エンドポイント(`Program.cs`のルーティングと処理)は、2つの基盤で完全に共通。基盤ごとに違うのは次の3か所だけ。

| 違い | ECS版 | サーバーレス版 | 関連するADR |
|---|---|---|---|
| データアクセスの実装 | `EfTodoStore`(EF Core) | `DynamoTodoStore`(AWS SDK) | [ADR-0030](adr/0030-extract-todo-store.md) |
| 実装の選び方 | 設定値`Storage:Provider`が未指定(既定) | `Storage:Provider=DynamoDb` | [ADR-0030](adr/0030-extract-todo-store.md) |
| ホスティング | Kestrelで待ち受ける | `AddAWSLambdaHosting()`がLambdaのイベントをHTTPリクエストに変換する(Lambda以外では何もしない) | [ADR-0031](adr/0031-lambda-hosting-model.md) |
| コンテナイメージ | Dockerfileの`runtime`ステージ(`aspnet`ベース) | Dockerfileの`lambda`ステージ(Lambdaのベースイメージ) | [ADR-0034](adr/0034-dockerfile-multi-target.md) |

`Program.cs`に追加したのは、`AddAWSLambdaHosting()`の1行と、設定値で実装を切り替える分岐だけ。ビルドの手順(`dotnet publish`)も共通で、最後にどちらのベースイメージに包むかだけが違う。

## 2. コスト

### 待機コスト(アクセスがなくても毎月かかる費用)

| | ECS版 | サーバーレス版 |
|---|---|---|
| 普段(ECS版は落としている状態) | ほぼ0(ECRの保存代のみ) | ほぼ0(ECRの保存代のみ。数百MBで月数円) |
| 公開URLを常設する場合 | 月$35前後: RDS 約$21(db.t4g.micro、gp2 20GB。実績から計算)、Fargateのタスク1つ 約$11(0.25 vCPU、0.5GB)、パブリックIPv4アドレス 約$3.6、Secrets Manager 約$0.4 | ほぼ0(使われた分だけ課金) |

ECS版は、使っていない時間も「動いていること」に料金がかかる。そのため、普段はRDSやサービスごと削除し、必要なときに`terraform apply -var ecs_enabled=true`で作り直している([ADR-0029](adr/0029-ecs-rds-on-demand.md))。サーバーレス版は、アクセスがなければ料金がかからないので、公開URLを常設できる([ADR-0028](adr/0028-serverless-database.md))。

### 最悪の場合(公開URLに大量のアクセスがあった場合)

サーバーレス版は、使われた分だけ料金がかかるので、裏返すと、荒らされると料金が増える。4層の防御で上限を設けている([ADR-0036](adr/0036-public-url-protection.md))。

- API Gatewayのスロットリングは、rate 1 rps・burst 5に設定した。負荷をかけて計測したところ、実効の上限は約6 rpsだった(ベストエフォートのため、設定値どおりには効かない)
- 約6 rpsで1か月受け続けた場合、最悪で月$25前後と見積もった
- 月$10の予算アラートとCost Anomaly Detectionで、そうなる前に気づけるようにしている

ECS版は、タスクの数が固定なので、アクセスが増えても料金はほとんど増えない(増えるのはデータ転送料くらい)。その代わり、処理しきれない分は遅くなるか、失敗する。

## 3. 起動と応答の速さ

手元(日本国内)からcurlで計測した。サーバーレス版は条件ごとに5回の平均。

| | ECS版 | サーバーレス版(1024MB、ReadyToRun) |
|---|---|---|
| 起動にかかる時間 | タスクの起動に約25秒(うちイメージの取得が約7秒)。起動後の最初のリクエストに約0.8秒 | コールドスタート全体で約1.46秒(初期化 約0.5秒、最初のリクエストの処理 約0.7秒、API Gateway 約0.25秒) |
| 起動が起きるタイミング | デプロイやタスクを増やすときだけ。起動後は動き続ける | しばらくアクセスがないたび |
| 起動後の応答(ウォーム) | 約22ms | 約76ms |

- ウォームの応答の差(約50〜60ms)は、純粋な処理速度の差ではない。入口の条件が揃っていないためで、curlで段階ごとに分けて測ると、次の内訳だった
  - サーバーレス版(毎回新しく接続した場合、約80ms): DNS 約2ms、TCP接続 約8ms、TLSのハンドシェイク 約14ms、リクエストから応答まで 約55ms。同じ接続を使い回すと約48ms
  - ECS版はHTTPでタスクに直接つないでいるので、TLSの分(約14ms)がない。TCP接続の分を除いた、リクエストから応答までは約10ms程度
  - つまり差のうち、約14msはHTTPSかHTTPかの違いで、残りの約40msがAPI GatewayとLambdaの呼び出しの分と考えられる
- ECS版の手前にALBを置けば、条件はより揃う(ALBを通る分の上乗せと、HTTPSにする場合のTLSの分が乗る)。ただし、ALBを置いた構成は計測していない。ALBは月$20前後かかるため、ECS版では置いていない([ADR-0005](adr/0005-stage2-network-architecture.md))
- ECS版は、起動に時間がかかるが、その後は動き続けるので、利用者が起動を待つことはほとんどない。サーバーレス版は、起動は速いが、アクセスが途切れるたびに起動し直すので、利用者が待つ場面が繰り返し起きる。「起動の速さ」が、ECS版ではほとんど気にならず、サーバーレス版では利用者の体験に直結する

### サーバーレス版のコールドスタートの内訳([ADR-0035](adr/0035-cold-start-strategy.md))

| 条件 | 初期化 | 最初のリクエストの処理 | 利用者の待ち時間 |
|---|---|---|---|
| 512MB、ReadyToRunあり | 約550ms | 約1,460ms | 約2.26秒 |
| 1024MB、ReadyToRunあり(採用) | 約500ms | 約700ms | 約1.46秒 |
| 1024MB、ReadyToRunなし | 約570ms | 約960ms | 約1.76秒 |

- いちばん効いたのはメモリ(=CPU)。1024MBにすると、最初のリクエストの処理が半分になった。課金される時間も短くなるので、コールドスタート1回あたりの料金はほぼ変わらない
- ReadyToRunの効果は約0.3秒で、主に最初のリクエストの処理に効いた
- Native AOTを使えばさらに速くなるが、ECS版と共有しているコードに手を入れる必要があるため、採用していない

## 4. 運用のしやすさ

| 観点 | ECS版 | サーバーレス版 |
|---|---|---|
| ネットワーク | VPC、サブネット、ルートテーブル、セキュリティグループ、RDS用のサブネットグループを設計・管理する | 不要。DynamoDBはVPCの外にあるAWSのAPIで、IAMで認証する |
| DBの準備 | テーブルは起動時のマイグレーションで作る([ADR-0008](adr/0008-migration-strategy.md))。認証情報はSecrets Managerから渡す | テーブル(キーとTTL)はTerraformで作る。マイグレーションや認証情報の受け渡しはない |
| データの形 | DBが保証する(列の型、NOT NULLなど) | キー以外はアプリが保証する。DBは形の違うデータも受け付ける |
| スケール | タスクの数を自分で決める | 自動。上限は防御の設定(スロットリング、同時実行数)で決める |
| デプロイ | タスク定義の新しいリビジョンを登録し、サービスを更新する | `update-function-code`でイメージを差し替える |
| 落とす・作り直す | RDSを作り直すとSecretのARNが変わるため、タスク定義もセットで作り直す仕組みが必要だった([ADR-0029](adr/0029-ecs-rds-on-demand.md)) | 落とす必要がない(待機コストがほぼ0) |
| 防御 | セキュリティグループで通信元を絞る | スロットリング、同時実行数、DynamoDBの最大スループット、予算アラートの4層 |

## 5. RDBからNoSQLに移して、失ったものと得たもの

**失ったもの**
- 自由な検索: RDBでは後から任意のクエリを書けた。DynamoDBでは、キー以外で引くにはGSIなどを事前に設計する必要があり、アクセスパターンを先に決める必要がある([ADR-0037](adr/0037-dynamodb-table-design.md))
- 集計やJOIN: DynamoDBではほぼできない
- データの形の保証: キー以外の属性の型や有無を、DBは検査しない
- 件数の上限の効率: 一覧の上限(`Take(100)`)は、EF Coreでは`LIMIT`にならず、DynamoDBでもScanを途中で止める形で実現した([ADR-0038](adr/0038-list-limit.md))

**得たもの**
- 待機コストがほぼ0になった
- VPCやマイグレーション、認証情報の受け渡しが要らなくなった
- データの自動削除(TTL)を、追加料金なしで使える
- キーで引く限り、データ量が増えても性能がほぼ一定

今回のAPIは、読み方が「IDで1件」と「一覧」の2つだけで固定なので、DynamoDBの向いている条件に入っている。検索や集計の要求が増えるなら、RDBの方が向いている。

## 6. どちらを選ぶか

| 条件 | 向いている方 |
|---|---|
| アクセスが少ない、または波がある | サーバーレス版(待機コストがほぼ0) |
| アクセスが常に多い | ECS版(常時稼働の料金が、リクエスト課金より安くなる) |
| 応答の速さを常に一定にしたい | ECS版(コールドスタートがない) |
| ネットワークや基盤の管理を減らしたい | サーバーレス版 |
| 検索や集計の要求が増えていく | ECS版(RDB) |
| 読み方が決まっていて、量が多い | サーバーレス版(DynamoDB) |

このリポジトリでは、面接で動作を見せるための公開URLを常設する用途から、サーバーレス版を公開用とし、ECS版は普段は落として、必要なときにコードから再現できる状態にしている。
