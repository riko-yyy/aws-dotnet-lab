# ADR-0019: Terraform Stateの保存先

## 論点
Terraformの状態(`.tfstate`、コード上の名前と実際のAWSリソースの対応表)をどこに保存するか。

## 選択肢
- A案: ローカルのファイル(`terraform.tfstate`)にそのまま保存
- B案: S3バケットに保存(リモートバックエンド)

## 決定
B案(S3バックエンド)。ロック機構は、DynamoDBテーブルを別途用意せずTerraform 1.10以降のネイティブS3ロック機能(`use_lockfile = true`)を使う。

## 理由
- 複数人・複数端末での共有、ロックによる排他制御、耐久性(バージョニング)、機密情報の管理のしやすさといった観点で、実務標準の構成を体験しておく価値がある
- S3バケット自体のコストはほぼ無料で、個人ラボでも気軽に導入できる
- Terraform 1.10以降のネイティブS3ロックにより、DynamoDBテーブルという追加リソースを用意せずに済む

## 却下した選択肢
- A案(ローカルファイル): 個人のソロプロジェクトなのでA案でも実用上は困らないが、実務で使われる構成の学習を優先してB案にした

## 補足
State保存用のS3バケット(`todo-api-terraform-state-737816144781`)自体は、Terraformで管理せず手動(コンソール)で作成した。これは「Stateの保存先を、Terraformで管理しようとすると鶏と卵の問題になる」ための定石。
