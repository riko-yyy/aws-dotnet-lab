# ADR-0001: Toy APIの題材

## 論点
学習用のToy APIとして、どのようなドメインを題材にするか。

## 選択肢
- A案: 完全に抽象的な題材(例: `Item` をCRUDするだけのAPI)
- B案: 多少ストーリー性のある題材(例: 簡易な在庫管理、TODO管理)
- 業務ドメインを模した本格的な題材(例: 実務に近い受発注管理など)

## 決定
B案。具体的な題材はTODO管理とする。ただしドメインは `Title` / `Done` 程度の最小構成に留める。

## 理由
- 本リポジトリの目的は「動くプロダクトを作ること」ではなく「インフラの意思決定記録を残すこと」
- 完全に抽象的な題材(A案)よりも、TODO管理のようにストーリー性がある方がアウトプットとして見せやすい
- 一方でドメインを凝りすぎると、後続段階(RDS連携やCRUD実装)で「業務ロジックの設計」に時間を取られ、本来の目的(インフラの意思決定)から逸れるリスクがある。そのためドメインは意図的に薄く保つ

## 却下した選択肢
- 業務ドメインを模した本格的な題材: リポジトリの目的(インフラ学習)から外れて過剰。ドメインモデリングそのものが目的化してしまう
