# ADR-0032: サーバーレス版の入口にAPI GatewayのHTTP APIを使う

## 論点
サーバーレス版の公開URLを、何で受けるか。

## 背景
公開URLは、面接官に「動いている証拠」として見せるために常設する。誰でもアクセスできるので、大量のアクセスがあった場合に課金が増え続けないよう、防御が必要になる。DBにはオンデマンドのDynamoDBを使っていて、課金に上限がない([ADR-0028](0028-serverless-database.md))。

## 選択肢
- API Gateway(HTTP API): 100万リクエストあたり約$1強。ステージ単位でスロットリング(1秒あたりのリクエスト数とバースト)を設定できる
- API Gateway(REST API): 100万リクエストあたり約$3.5以上。利用プラン、APIキー、WAFなど機能が豊富
- LambdaのFunction URL: 追加料金なし。防御の手段はLambdaの同時実行数の上限だけ

## 決定
API GatewayのHTTP APIを採用する。

## 理由
- 「コスト最小」ではなく、**課金の上限を読めること**を優先した。いちばん安いのはFunction URLだが、防御の手段が同時実行数の上限しかない
  - 同時実行数の上限で制限できるのは「同時に動く数」で、「リクエストの数」ではない。例えば上限が2でも、処理が1回50msなら1秒に約40回実行され、その分の課金は続く
  - HTTP APIのスロットリングなら「1秒に何リクエストまで」を制限できる。超えたリクエストには429を返し、LambdaもDynamoDBも呼ばれない
- 待機コストはゼロのまま。HTTP APIはリクエスト単位の課金なので、アクセスがなければ料金はかからない。ここまでの方針(待機コストをゼロに近づける)と矛盾しない
- 具体的なスロットリングの値と、Lambdaの同時実行数の予約を組み合わせるかどうかは、公開URLの防御としてまとめて別途判断する

## 却下した選択肢
- REST API: 利用プランやWAFは今回の規模には過剰で、料金もHTTP APIの3倍以上
- Function URL: 無料で設定も最も簡単だが、リクエストの数を制限できない。認証の選択肢も、IAM認証か認証なしの2つだけ

## トレードオフ
- HTTP APIでは、WAFを直接つなげられない。APIキーによる利用プランもない。より細かい防御が必要になったら、REST APIへの切り替えか、前段にCloudFrontを置くことを検討する
- リクエストごとの課金(わずかだが)が、Function URLより増える
