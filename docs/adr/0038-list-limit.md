# ADR-0038: 一覧の件数の上限は、遅延実行を前提にエンドポイントで掛ける

## 論点
一覧(`GET /todos`)で返す件数に上限を設けるか。設けるなら、どこで掛けるか。

## 背景
- サーバーレス版は公開URLで、誰でもデータを追加できる。スロットリング(rate 1 rps、[ADR-0036](0036-public-url-protection.md))の範囲内でも、1日で最大8万件ほど追加されうる
- TTL(7日、[ADR-0037](0037-dynamodb-table-design.md))だけでは、その間に大量に追加されることは防げない
- 一覧はDynamoDBではScanになり、件数に比例して読み取りの量と料金が増える

## 選択肢
- A: インフラ層の実装(`EfTodoStore`と`DynamoTodoStore`)のそれぞれに、取得の上限を入れる
- B: `ITodoStore.GetAllAsync()`を`IAsyncEnumerable<TodoItem>`(遅延実行)にし、エンドポイント(`Program.cs`)で`Take(100)`を掛ける
- C: 上限を設けない

## 決定
Bを採用する。上限は100件とする。

## 理由
- 上限は「アプリとしていくつまで返すか」という方針なので、エンドポイントの1か所に置く。インフラ層の実装は、上限を知らずにデータを流すだけにする。Aでは同じ方針が2つの実装に散らばり、片方だけ変えるおそれがある
- 遅延実行なので、DynamoDB版では上限を超えた分を読まない。`DynamoTodoStore`はScanを100件ずつ読み進め、`Take(100)`で列挙が止まると、次のScanは発行されない。料金と読み取りの上限(ADR-0036の3層目)を守れる
- .NET 10では`IAsyncEnumerable`用のLINQ(`Take`など)が標準ライブラリに入っており、追加のパッケージが要らない。Minimal APIは`IAsyncEnumerable`をそのまま返せる

## 却下した選択肢
- A: 同じ方針がインフラ層の2か所に散らばる
- C: 荒らされると一覧が遅くなり、DynamoDBの上限にも引っかかって、一覧が常に失敗するようになる

## トレードオフ
- RDS版では、`Take(100)`はSQLの`LIMIT`にならない。`IAsyncEnumerable`の`Take`はC#側で列挙を止めるだけなので、SQLは全件を取得するクエリのまま発行される。100件を受け取った時点で読むのをやめるが、DB側では全件のクエリが動く。`LIMIT`にするには`IQueryable`を返す必要があるが、DynamoDBには`IQueryable`の仕組みがなく、共通のインターフェースにできない。RDS版は公開しておらず件数も少ないので、実害はないと判断した
- 一覧は最大100件で、101件目以降を取る手段(ページ分け)はない。今の用途(動作の確認)では不要と判断した
- 一覧のAPI仕様が変わる(これまでは全件)。ECS版とサーバーレス版の両方で同じ仕様になる
