# ADR-0028: サーバーレス版のDBにDynamoDBを採用する

## 論点
同じTODO APIをLambdaに載せ替えるサーバーレス版で、どのDBを使うか。

## 背景
- ECS版はRDS for PostgreSQL([ADR-0007](0007-database-engine.md))。2026年9月の実績では、RDS(db.t4g.micro、gp2 20GB)は1日約$0.69で、月に換算すると約$21(Secrets Managerと税を含めると約$24)。アクセスがなくても発生する待機コストである
- サーバーレス版は公開URLを常設し、「動いている証拠」として見せる用途。常に稼働させる前提なので、待機コストはそのまま毎月の固定費になる

## 選択肢
- RDS for PostgreSQLを継続する
- Aurora Serverless v2(0 ACUまで自動で一時停止させる)
- DynamoDB(オンデマンドキャパシティ)

## 決定
DynamoDB(オンデマンドキャパシティ)を採用する。

ECS版はRDS for PostgreSQLのまま([ADR-0007](0007-database-engine.md))とする。データアクセスをインターフェースで切り出し、RDB実装とDynamoDB実装の2つを持つ。

## 理由
- 待機コストがほぼゼロ。オンデマンドはリクエスト単位の課金で、ストレージは25GBまで無料枠がある
- DynamoDBはVPCの外にあるAWSのAPIで、IAMで認証する。そのためLambdaをVPCに置く必要がない(サブネットやセキュリティグループの設計が不要)
- スキーマがないので、EF Coreのマイグレーション([ADR-0008](0008-migration-strategy.md))に相当する仕組みが不要
- 「RDBからNoSQLに載せ替えて、何を失い何を得たか」を比較の題材にできる

## 却下した選択肢
- RDS継続: 常設の公開URLとは、月約$24の待機コストが見合わない。LambdaをVPCに置く必要もある。ECS版と同じインスタンスを共有する案は、ECS版のRDSを普段は削除しておく方針([ADR-0029](0029-ecs-rds-on-demand.md))と両立しない
- Aurora Serverless v2: EF CoreとPostgreSQLをそのまま使える点は魅力的。ただし、次の2点で見送った
  - 再開に時間がかかる: 一時停止からの再開に十数秒かかる。公開URLへの最初のアクセスでは、Lambdaのコールドスタートとこの待ち時間が重なる
  - 待機コストがゼロにならない: 0 ACUまで縮小しても、ストレージ代とSecrets Managerの料金は残る。DynamoDBなら、無料枠の範囲に収まる
  - あわせて、LambdaをVPCに置く必要もある

## トレードオフ(失うもの)
- 主キー以外で検索するには、事前の設計が必要になる。例えば全件一覧はScanになり、完了済みだけの絞り込みにはGSIなどが要る。RDBでは後から自由にクエリを書けたが、DynamoDBではアクセスパターンを先に決める必要がある
- EF Coreが使えないため、DynamoDB用の実装を別に書く必要がある。データアクセスを切り出すことが前提になる
- オンデマンドは課金に上限がない。公開URLに大量のアクセスがあれば、そのままコストになる。スロットリングと予算アラートで対策する(別途ADRに記録する)
