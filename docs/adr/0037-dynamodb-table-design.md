# ADR-0037: DynamoDBのテーブルはIDだけをキーにし、7日のTTLで自動削除する

## 論点
サーバーレス版のDynamoDB([ADR-0028](0028-serverless-database.md))で、テーブルのキーをどう設計するか。また、公開URLで誰でもデータを追加できる状態で、データが増え続けることにどう対処するか([ADR-0036](0036-public-url-protection.md)の補足で残した宿題)。

## 背景
DynamoDBのテーブルは、`Dictionary`に近い。キーで引くのは速いが、それ以外の探し方はテーブル全体を順に読む(Scan)しかない。そのため、「どう引くか」を先に決めて、それに合わせてキーを設計する。

このAPIの読み取り方は、「IDで1件」と「全件の一覧」の2つだけ。

## 選択肢
キーの設計:
- A: パーティションキーを`id`だけにする。一覧はScan(`Dictionary<Guid, TodoItem>`を全件`foreach`するのに相当)
- B: パーティションキーを固定値(`"TODO"`)、ソートキーを`id`にする。一覧は1つのパーティションへのQuery(`Dictionary<string, SortedList<Guid, TodoItem>>`で、キーが1つだけの形に相当)

データが増え続けることへの対処:
- TTLで、作成から一定期間たったデータを自動削除する
- 何もしない

## 決定
- キーはAとし、パーティションキー`id`(文字列)だけのテーブルにする。ソートキーやGSIは持たない
- TTLを使い、作成から7日で自動削除する。属性`expiresAt`(UNIX時間の秒)を追加時に書き込み、テーブルのTTL設定でこの属性を指定する
- 更新してもTTLは延ばさない(作成から7日で消える)

## 理由
- 読み取り方が「IDで1件」と「全件」だけなので、Aで足りる。Bの利点は並び順が付くことだが、今のAPIは並び順を約束していない(EF Core版の一覧も`ORDER BY`を付けていない)。どちらも一覧では全件を読むので、読み取りの量も変わらない
- TTLによる削除は、DynamoDBが追加料金なしで行う。削除のための処理を書く必要もない
- 7日にしたのは、面接官が動作を確かめるには十分で、荒らされた場合にも1週間で元に戻るため

## 却下した選択肢
- B(固定値のパーティションキー): 並び順が要らない今のAPIでは、利点がない。固定値をキーにするのも、小技っぽさがある
- 何もしない: 誰でもデータを追加できるため、件数が増えるとScanが遅くなり、DynamoDBの読み取りの上限(ADR-0036の3層目)にも引っかかる

## トレードオフ
- TTLはサーバーレス版だけの動きで、ECS版(RDS)のデータは自動では消えない。同じAPIでも、基盤によってデータの寿命が違うことになる。ECS版は公開しておらず、普段はRDSごと削除しているので([ADR-0029](0029-ecs-rds-on-demand.md))、実害はない
- TTLは期限ちょうどに消えるわけではなく、期限が過ぎてから数日以内に削除される。期限切れでも、しばらくは一覧に出ることがある
- TTLだけでは、7日の間に大量に追加されることは防げない。一覧の件数の上限と組み合わせる([ADR-0038](0038-list-limit.md))

## 補足
テーブルは、アプリではなくインフラ側で作る。AWS上ではTerraform、ローカルのDynamoDB Localではdocker composeの`dynamodb-init`サービスがCLIで作る。
