# ADR-0036: 公開URLの防御は4層で考え、外側をいちばんきつくする

## 論点
サーバーレス版の公開URLは、誰でもアクセスできる。大量のアクセスがあったときに、課金が増え続けないようにするには、どう防御するか。

## 背景
- 入口にはAPI GatewayのHTTP APIを使う。スロットリングの具体的な値は、ここで決めることにしていた([ADR-0032](0032-serverless-entry-point.md))
- DBはオンデマンドのDynamoDBで、課金に上限がない([ADR-0028](0028-serverless-database.md))
- 既存の予算(My Zero-Spend Budget)は、実績が$0.01を超えたら通知する設定。RDSがある限り毎月必ず鳴り、しかも通知は1つのしきい値につき月1回だけ。そのため、月の途中で起きた急な増加には気づけない

## 決定
防御を4層に分ける。1〜3層は「止める」仕組みで、4層は「気づく」仕組み。

| 層 | 仕組み | 値 |
|---|---|---|
| 1. 入口 | HTTP APIのスロットリング | rate 1 rps、burst 5 |
| 2. 実行 | Lambdaの同時実行数の予約 | 5 |
| 3. DB | DynamoDBのオンデマンドの最大スループット | 読み取り・書き込みとも10/秒 |
| 4. 検知 | 予算アラートとCost Anomaly Detection | 月$10(実績80%、100%、予測100%で通知)。Cost Anomaly Detectionも有効にする |

1〜3層はTerraformで管理する。4層はアカウント全体のリソースなので、IAM Access Analyzerと同じように([ADR-0023](0023-iam-access-analyzer.md))、コンソールで作り、Terraformの管理外に置く。Zero-Spend Budgetは、新しい予算を作ったあとに削除する(先に削除すると、監視のない期間ができるため)。

## 理由
- **料金の上限を決めるのは、1層目のrateだけ**
  - rateを1 rpsにすると、攻撃されて1か月ずっと上限まで受け続けたとしても、リクエストは約260万回。HTTP API、Lambda、DynamoDBを合わせても、月$4〜6程度に収まる(概算。実装後に実際の料金で確かめる)
  - burstは瞬間的に受け付ける量で、長い期間で平均すると流量はrateを超えない。そのため、burstを小さくしても最悪の場合の月額はほとんど変わらない
  - 2層目と3層目には、1層目を通過したリクエストしか届かない。そのため、2層目と3層目をきつくしても料金はそれ以上下がらない
- **外側をいちばんきつくし、内側は保険として緩めにする**
  - 内側を外側より狭くすると、そこが本当のボトルネックになる。入口で意図して決めた制限とは別の場所で詰まり、原因も追いにくくなる
  - 2層目と3層目は、1層目が破られたとき(設定ミスや、API Gatewayを経由しない呼び出し)の保険として置く
- 予算は、待機コスト(RDSを削除したあとは月$1未満)より上で、最悪の場合の月額に近い値に置く。予測の通知で、最悪の場合に近づいていることを月末より前に知るため
- Cost Anomaly Detectionは、固定額の予算では拾えない、サービス単位・日単位の急な増加を拾う

## 却下した選択肢
- **すべての値を最小(1)にする**: 料金は下がらず、正常なアクセスが失敗する原因だけが増える
  - burst 1: ダブルクリックや、画面が一度に2つ送るリクエストの2つ目が429になる
  - Lambdaの同時実行数 1: コールドスタートの間(ASP.NET Coreの起動で1秒以上かかる見込み)に来た2つ目のリクエストが、Lambdaの側で拒否される。API Gatewayの429より分かりにくいエラーになる
  - DynamoDB 1/秒: 上限の単位は「リクエストの数」ではなく「読み書きのユニット数」。一覧はScanで、テーブル全体のデータ量に比例してユニットを消費する。公開URLなので誰でもTODOを追加でき、データが増えるとScan 1回で上限を超え、一覧が常に失敗するようになる
- **予算アラートだけで守る**: 予算は「気づく」仕組みで、課金を止めない。AWS Budgetsのデータの更新も1日に数回で、即時ではない
- **Budget Actionsで自動的に止める**: Budget Actionsで実行できるのは、IAMポリシーの適用や、EC2とRDSの停止などに限られる。Lambdaを止める用途には向かない。止める役割は1〜3層に任せる

## 補足
- 予算アラートは、ECS版のRDSを削除する仕組み([ADR-0029](0029-ecs-rds-on-demand.md))ができたあとに作る。RDSがある間は、月$10の予算をすぐに超えてしまい、警報として意味をなさないため
- DynamoDBの一覧がScanであることは、データが増えると3層目の上限にも、料金にも効いてくる。公開URLで誰でもデータを追加できる状態のため、件数の上限やデータの定期的な削除が必要かどうかは、DynamoDBの実装のときに検討する
